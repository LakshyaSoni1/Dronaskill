SLIDE 2 — THE PROBLEM
====================================================================
SLIDE CONTENT:

  same playlist regardless of what they already know
- Free learning content exists, but it's scattered across YouTube,
  ridden with ads, comments, and "recommended for you" distractions

  platforms or college placement cells

SAY THIS:
Ground this in something relatable: "Raise your hand if you've ever
opened YouTube to learn one concept and closed the tab 40 minutes
later on a completely unrelated video." That's the exact failure mode
DronaSkill's lecture player is built to prevent.

====================================================================
SLIDE 11 — LECTURE LIBRARY: PLAYLIST MODE (TECHNICAL HIGHLIGHT)
====================================================================
SLIDE CONTENT:
- Learners can paste any YouTube playlist link and swap it in for a
  skill's curated list
- No YouTube Data API key required — and none exists for this static
  site — so playlist contents come live from the client-side YouTube
  IFrame Player API instead
- Video titles/channels resolved through YouTube's public oEmbed
  endpoint, also key-free
- Duration for playlist videos isn't available up front from any
  key-free source — the player measures it itself the first time a
  video is watched to completion, then caches it for accurate
  auto-logging from then on

SAY THIS:
This is your strongest "we actually engineered something" slide — use
it if the audience is technical. The key insight to say out loud: "We
don't have a backend, so we can't hold an API key. Every integration
had to work from the browser alone, key-free" — that constraint, not
its absence, is the interesting part.

SLIDE 15 — TECHNICAL ARCHITECTURE
====================================================================
SLIDE CONTENT:
- 100% static: plain HTML files with inline CSS/JS — no framework,
  no bundler, no package.json
- Every page is self-contained and can be opened on its own
- Two shared data modules: skills-data.js (124-skill catalogue, 18
  tracks, plan-building logic) and lectures-data.js (curated video
  library) — the only shared code in the whole project
- All learner state lives in localStorage: profile, skill progress,
  study log, lecture overrides and watch history, interview sessions
- A small local launcher script serves the folder over
  http://localhost so YouTube embeds and the IFrame API work
  correctly (they refuse to run over a bare file:// origin)

SAY THIS:
Reframe "no backend" as a deliberate choice for a hackathon/early-
stage build, not a limitation the team failed to overcome: fast to
ship, zero hosting cost, zero attack surface for user data since
nothing leaves the browser. Then pivot straight into the roadmap
slide — "here's exactly where a backend earns its place."

====================================================================
ANTICIPATED QUESTIONS — HAVE ANSWERS READY
====================================================================

Q: "Why no backend / database at all?"
A: Deliberate early-stage choice — zero hosting cost, zero attack
   surface for user data (nothing leaves the browser), fastest
   possible path to a working product. The roadmap adds a backend
   specifically where it earns its place: real AI grading and
   cross-device accounts.

Q: "Isn't localStorage risky — what if a user clears their browser
   data?"
A: Yes, and that's precisely why cross-device accounts are the first
   roadmap item once a backend exists. Today's tradeoff was shipping
   speed over persistence guarantees.

Q: "How do you know the mock interview grading is any good if it's
   just a heuristic?"
A: We're explicit that it's a stand-in — keyword coverage, sentence
   length, filler-word detection. The real grading rubric (LLM-based,
   via Claude) is already fully written and mapped to the UI; it's
   waiting on backend infrastructure, not on design work.

Q: "What happens if a curated video gets taken down or disabled?"
A: Every video is pre-checked for embeddability before being added.
   Playlist-mode videos are resolved live from YouTube itself, so
   availability tracks YouTube directly.

Q: "How is this different from just... using YouTube?"
A: Curation (only vetted, embeddable videos), zero distractions (no
   suggested videos/comments/autoplay), and everything tied back into
   a measurable plan and progress dashboard — YouTube alone gives you
   none of the last two.

Q: "What's the actual tech stack?"
A: Plain HTML/CSS/JS, no framework, no build step. Two shared data
   modules for skills and lectures. All state in localStorage today.
   YouTube IFrame Player API + oEmbed for playlist mode, no API key
   needed anywhere.
